What the colours meanhide
Hue = which sector (9)
Brightness & form = what kind of quantity
Solid, bright — fractional attributed effort. The honest count: every commit split across sectors, weights summing to 1.
Ghost, faint — secondary reach beyond that effort. Where the ghost runs well past the solid, the old single-sector model was throwing that difference away.
Quadrant view — each limb takes a representative hue from its member sectors: copy, workflows, seo, coding.
Other marks
Dark red band — 2025-02, a month with no activity at all. A real pinch in the solid, never interpolated over.
Brown core — a drawn floor, not a measurement. Sectors at zero rest on it so the object stays readable.
t Badge colour = how a repo's weights were derived: topics from evidence, authored asserted by hand, single today's sector.
Gini Amber numbers are inequality figures, not counts.
Angle around the object is which sector — an ordered category, not a compass direction. Height is time.
The ruleset — where the weights come from

weight(sector) = share of that repo's GitHub topics mapping to it. Systematic, auditable, and an extension of the topic-map already in tree.config.yml — not a parallel mechanism. Topics captured 2026-08-01 and baked in; no API call at runtime.

Worked example — flickr-to-instagram-automation, 16 topics: 3 image (flickr-photos, gpt-4-vision, vision-api), 9 workflow, 4 agent → .19 / .56 / .25. That single repo moves 208 commits off a pure workflow reading.

Gini is inequality across the 9 sectors: 0 = every sector equal, 1 = one sector has everything. Lower means the tree grows in more directions, which is the whole reason to do this.
